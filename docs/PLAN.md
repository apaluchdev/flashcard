# Flashcard App — Implementation Plan

## 1. Goals

| # | Feature | Notes |
|---|---------|-------|
| F1 | Create and edit decks and text cards in the app | Plain text front/back; line breaks preserved |
| F2 | Import a deck from a `.json` file | Alternative to in-app creation; creates a new deck |
| F3 | Share decks via links | Every deck has a stable URL: `/decks/{id}` |
| F4 | Public / private visibility | **Public** = listed in search. **Private** = unlisted: hidden from search, but viewable by anyone with the link |
| F5 | Only the creator can edit a deck and its cards | Enforced on the server for every mutation |
| F6 | Search page | Two scopes: **My decks** (signed in) and **Public decks** |
| F7 | Study viewer | One card at a time, click/tap/keyboard to flip |
| F8 | Shuffle | Off by default (saved order); toggle to shuffle and back |

### Decisions made

- **Sign-in:** OAuth only (GitHub and Google). No passwords stored.
- **Private decks are unlisted:** a share link to a private deck works for anyone. Deck IDs are random UUIDs, so they can't be guessed.
- **Guests:** anyone can study shared or public decks and search public decks without signing in. Signing in is required only to create, edit or import decks, or to see "My decks".
- **Copying decks:** not included for now (see [Later](#9-later--out-of-scope)).

## 3. Architecture

```
Browser ──► Next.js (App Router)
             ├─ proxy.ts                quick redirect to /sign-in for protected routes (reads the cookie only)
             ├─ app/ (Server Components) pages read data through the data access layer
             ├─ Server Actions          create / update / delete / import; each one re-checks permissions
             ├─ /api/auth/[...all]      Better Auth handler (OAuth callbacks, session)
             └─ src/server/*            data access layer: the only code that queries the database
                       │
                       ▼
                 PostgreSQL (Docker)
```

**Security principle:** `proxy.ts` only redirects users for convenience. The real authorization happens in the **data access layer** (`src/server/`). Every write filters on `owner_id = currentUser.id`, so a forged request can't edit someone else's deck even if it skips the UI.

## 4. Data model

Better Auth creates `user`, `session`, `account` and `verification` tables (generated into `src/db/auth-schema.ts`). The app's own tables:

```ts
visibility = pgEnum("visibility", ["private", "public"])

decks
  id           uuid PK default random          // also the share-link id
  owner_id     text FK -> user.id ON DELETE CASCADE, NOT NULL
  title        text NOT NULL                   // 1–200 chars
  description  text NULL                       // ≤ 2,000 chars
  visibility   visibility NOT NULL default 'private'
  card_count   integer NOT NULL default 0      // stored copy of the card count, so search results don't need a join
  created_at   timestamptz default now()
  updated_at   timestamptz default now()
  INDEX (owner_id, updated_at DESC)            // "My decks"
  INDEX (visibility, updated_at DESC)          // "Public decks"
  GIN trigram INDEX on title, description      // text search (pg_trgm extension)

cards
  id           uuid PK
  deck_id      uuid FK -> decks.id ON DELETE CASCADE
  front        text NOT NULL                   // 1–5,000 chars
  back         text NOT NULL                   // 1–5,000 chars
  position     integer NOT NULL                // 0..n-1, the saved order
  created_at   timestamptz
  INDEX (deck_id, position)
```

Notes:
- Cards have no `owner_id`. Ownership always comes from the parent deck.
- `position` holds the saved order (F8). Saving a deck rewrites positions 0..n-1 in one transaction.
- Limits: at most **1,000 cards per deck** (enforced by zod and again in the server action).

### Access rules

| Action | Guest | Signed-in non-owner | Owner |
|--------|:-----:|:-------------------:|:-----:|
| View / study any deck by link (public or private) | ✅ | ✅ | ✅ |
| Deck appears in "Public decks" search | public only | public only | public only |
| Deck appears in "My decks" | — | — | ✅ (both visibilities) |
| Create / import a deck | ❌ → sign in | ✅ | ✅ |
| Edit title/description/cards, change visibility, delete | ❌ | ❌ (404) | ✅ |

Non-owners opening `/decks/{id}/edit` get a 404 page, not a 403, so the edit page doesn't confirm who owns what.

## 5. JSON import format

```json
{
  "title": "Spanish Basics",
  "description": "Common greetings and phrases",
  "visibility": "private",
  "cards": [
    { "front": "Hola", "back": "Hello" },
    { "front": "Gracias", "back": "Thank you" }
  ]
}
```

- `title` and `cards` are required. `description` is optional. `visibility` is optional and defaults to `"private"`.
- The card order in the file becomes the saved order.
- Unknown fields are ignored, so files exported from other tools still import.
- **Limits:** file ≤ 1 MB, `.json` only, 1–1,000 cards, same length limits as in-app editing.
- **Flow:** the browser reads and validates the file with the shared zod schema and shows a preview (title, card count, first few cards, any errors listed with their paths, e.g. `cards[3].back: required`). On confirm, the parsed JSON goes to a Server Action, which **validates it again** before inserting the deck and its cards in one transaction. The user is then redirected to the new deck.
- A **"Download example JSON"** link on the import tab gives users a correct template.
- Importing always creates a new deck. It never merges into an existing one.

## 6. Step-by-step implementation

Each phase ends with something that runs and can be committed. Tests are written in the phase that adds the code they test.

### Phase 0 — Foundations ✅
1. Install `zod`, `better-auth`, `vitest`, `@playwright/test`. Add the shadcn components listed in §2.
2. **Switch from `db:push` to generated migrations** (`drizzle-kit generate`, then commit `drizzle/`, then `drizzle-kit migrate`). Migrations are reviewable and reproducible across machines and deploys.
3. Add a `migrate` service to `compose.yaml`. It uses a small `migrator` stage in the Dockerfile to run `drizzle-kit migrate`, and `app` waits for it with `depends_on: condition: service_completed_successfully`. The production image stays small because it doesn't include drizzle-kit.
4. Extend `.env.example` with `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, `GITHUB_CLIENT_ID/SECRET`, `GOOGLE_CLIENT_ID/SECRET`. Pass them to `app` in compose.
5. App shell: `layout.tsx` with a header (logo, "Browse", "New deck", user menu placeholder), toaster, and a `container` width. Replace the Next.js starter `page.tsx`.

### Phase 1 — Authentication (OAuth) ✅
1. Register OAuth apps:
   - GitHub: Settings → Developer settings → OAuth Apps. Callback URL: `http://localhost:3000/api/auth/callback/github`
   - Google Cloud Console → Credentials → OAuth client. Redirect URI: `http://localhost:3000/api/auth/callback/google`
2. `src/lib/auth.ts`: Better Auth with the Drizzle adapter (Postgres) and the GitHub and Google social providers.
3. Define the auth tables in `src/db/auth-schema.ts`, then create a migration. The Better Auth CLI (`@better-auth/cli`) is deprecated and stuck at 1.4, so the tables are written by hand from the field definitions in `@better-auth/core` (`db/get-tables`). Re-check them when upgrading better-auth.
4. `app/api/auth/[...all]/route.ts`: mount the handler.
5. `src/server/session.ts`: `getCurrentUser()` (wrapped in React `cache`) and `requireUser()`, which redirects to `/sign-in?next=…`.
6. `/sign-in` page with provider buttons; the user menu shows avatar, name and "Sign out".
7. `proxy.ts`: if there's no session cookie on `/decks/new` or `/decks/*/edit`, redirect to `/sign-in`. This is only a convenience check (see §3).
8. **Done when:** you can sign in with GitHub and with Google, reloading keeps you signed in, and signing out works.

### Phase 2 — Deck and card schema ✅
1. Update `src/db/schema.ts`: `visibility` enum, `owner_id`, `card_count`, indexes, `pg_trgm` extension (in a custom migration).
2. Generate and apply the migration (`npm run db:generate`, then `npm run db:migrate`). The starter tables are empty, so adding the NOT NULL `owner_id` column is safe.
3. `src/lib/validation.ts`: `cardInput`, `deckInput` (with `cards: cardInput[]`) and `deckImportFile`, all built from the same base schemas.
4. Unit tests for the validation limits.

### Phase 3 — Create and edit decks (F1, F5)
1. **Data access layer** (`src/server/decks.ts`):
   - `getDeckForView(id)` returns the deck, its cards ordered by position, and the owner's name/avatar, or null. No permission check is needed because any deck is viewable by link.
   - `getDeckForEdit(id, userId)`: `WHERE id = $1 AND owner_id = $2`, so a non-owner gets null and then 404.
2. **Server Actions** (`src/server/deck-actions.ts`), each starting with `requireUser()` and zod parsing:
   - `createDeck(input)` inserts the deck and its cards in one transaction, then redirects to `/decks/{id}`.
   - `updateDeck(id, input)`: a transaction that checks ownership (`WHERE owner_id`), updates the metadata, then compares cards by id: deletes removed ones, updates existing ones, inserts new ones, and rewrites `position` and `card_count`.
   - `deleteDeck(id)`: an owner-only delete; cards are removed by the cascade.
   - Each action calls `revalidatePath` for affected routes.
3. **`deck-form.tsx`** (client), used by both `/decks/new` and `/decks/[id]/edit`:
   - Title, description, visibility switch.
   - Card list: front/back textareas, "Add card", delete, move up/down (drag-and-drop can come later).
   - Client-side validation with the same zod schema; warning about unsaved changes before leaving the page.
4. Edit page: "Delete deck" behind an `alert-dialog` confirmation.
5. Owner-only "Edit" button on the viewer page.
6. **Done when:** a user can create a deck with cards, edit them, reorder them, delete the deck, and cannot reach or submit edits to another user's deck (checked by a test that calls the action directly with a different user).

### Phase 4 — Study viewer (F7, F8)
1. `/decks/[id]/page.tsx` (server component) loads the deck with `getDeckForView` and shows the title, description, owner, card count and share button, then renders `<CardViewer cards={…} />`.
2. `card-viewer.tsx` (client):
   - State: `order` (array of indexes), `current`, `flipped`.
   - The card flips with a CSS 3D rotation (`transform: rotateY(180deg)`, `backface-visibility: hidden`). The animation is skipped when the user has `prefers-reduced-motion` set.
   - Controls: Prev / Next, a "3 / 20" counter, and a progress bar.
   - **Shuffle toggle:** off shows the saved order; on applies a Fisher–Yates shuffle (`lib/shuffle.ts`) and returns to card 1. Turning it off restores the saved order. It isn't saved and resets on reload.
   - Keyboard: `Space`/`Enter` flips, `←`/`→` navigate, `S` toggles shuffle. The card is a `button` with an `aria-live` label so screen readers announce which side is showing.
   - Moving to another card always shows its front.
   - End of deck: a "You've reached the end" state with "Restart" and "Shuffle & restart".
   - Mobile: large tap targets; swipe support is optional.
3. Empty-deck state (0 cards): a message, plus a link to add cards if the viewer is the owner.
4. Unit test for `shuffle` (keeps all items, returns a new array, doesn't mutate its input).

### Phase 5 — Sharing and visibility (F3, F4)
1. `share-button.tsx` copies `{origin}/decks/{id}` to the clipboard with a toast. It uses the native share sheet (`navigator.share`) on mobile when available.
2. A visibility badge on the viewer and on search tiles ("Public" / "Private — only people with the link").
3. `setVisibility(id, visibility)`, an owner-only server action, so the owner can switch it from the viewer page without opening the editor.
4. `generateMetadata` on `/decks/[id]` gives shared links a proper title and description in chat and social previews. Private decks get `robots: noindex`.

### Phase 6 — JSON import (F2)
1. The `/decks/new` page gets tabs: **Build** (deck-form) and **Import JSON**.
2. `import-form.tsx`: file input (`accept=".json,application/json"`), size check, `JSON.parse` with a readable error message, `deckImportFile.safeParse`, a preview card showing title, card count and the first 3 cards, and the list of errors.
3. `importDeck(data)` server action: `requireUser()`, parse the data again with zod, reuse the `createDeck` insert logic, redirect to the new deck.
4. Serve an example file at `public/deck-example.json` and link to it.
5. Unit tests: valid file, missing title, empty cards, 1,001 cards, extra fields ignored, wrong types.

### Phase 7 — Search and browse (F6)
1. `searchDecks({ q, scope, userId, page })` in the data access layer:
   - `scope=public`: `visibility = 'public'`
   - `scope=mine`: `owner_id = userId` (requires sign-in; guests see a sign-in prompt)
   - `q`: `title ILIKE %q% OR description ILIKE %q%` (fast thanks to the trigram index), ordered by best match when `q` is set and by `updated_at DESC` otherwise.
   - Pagination: 24 per page. Returns rows plus a `hasMore` flag.
2. `/decks` page: tabs (Public / My decks), a search input that updates `?q=` after a short delay (debounced), and a grid of `deck-card` tiles showing title, description excerpt, card count, owner, visibility badge and last-updated date. Includes empty and loading states.
3. Everything lives in the URL (`?scope=mine&q=spanish&page=2`), so search results can be bookmarked and shared.
4. The landing page shows the latest public decks and a hero with "Create a deck" and "Browse".

### Phase 8 — Polish and hardening
1. `not-found.tsx` and `error.tsx` for `/decks/[id]`, and `loading.tsx` skeletons.
2. Responsive pass (phone width), dark-mode check, keyboard and focus check.
3. Rate-limit the create and import actions per user (Better Auth has a rate limiter; a simple per-user limit inside the actions is enough).
4. Make sure no action trusts client-sent `ownerId` or `position` values. The server derives both.
5. Security headers in `next.config.ts` (CSP, `X-Content-Type-Options`, `Referrer-Policy`).

### Phase 9 — End-to-end tests and CI
1. Playwright tests against `docker compose up` with a seeded test user. For tests, sign in by creating a session in the database directly (a test-only helper), so the tests don't depend on GitHub or Google.
2. Test flows: create deck, study (flip, next, shuffle), share link opened by a guest, private deck missing from public search, non-owner can't edit, JSON import happy path and error path.
3. GitHub Actions: lint, typecheck, vitest, build Docker image, Playwright.

## 8. Risks and how they're handled

| Risk | Mitigation |
|------|-----------|
| Authorization bug lets a user edit someone else's deck | Ownership is checked in the SQL `WHERE` of every write, plus a dedicated test |
| OAuth setup friction (callback URLs, secrets) | Documented in Phase 1; separate OAuth apps for localhost and production |
| Large or malicious JSON uploads | 1 MB limit, card cap, zod validation on the server, text rendered as plain text (never as HTML) |
| Search getting slow as the number of decks grows | Trigram index from day one; can move to Postgres full-text search later |
| Slow hot reload in Docker on Windows | Develop with `npm run dev` on the host; Docker runs only Postgres (already set up) |
